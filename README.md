# Study — Приложение для управления обучением

## Описание проекта

Проект представляет собой REST API для образовательной платформы, разработанной с использованием Django и Django REST Framework.
Позволяет управлять курсами, уроками, пользователями и платежами.
Поддерживает фильтрацию, сортировку и вывод связанных данных.
Доступ к API открыт без аутентификации.


---

## 1. Настройка проекта

- Создан Django-проект с приложениями: `study`, `users`
- Подключены:
  - Django REST Framework — для реализации API
  - django-filter — для расширенной фильтрации данных
- Настроена обработка медиафайлов для загрузки изображений и аватаров

## 2. Модели

### Приложение users

#### Модель пользователя.
Реализована кастомная модель пользователя, наследованная от `AbstractUser`.  
Аутентификация осуществляется по электронной почте.  
Дополнительные поля профиля:
- Номер телефона
- Город проживания
- Аватар

#### Модель Payment (Платеж)

| Поле           | Описание                                     |
|----------------|----------------------------------------------|
| user           | Пользователь, совершивший оплату             |
| date_pay       | Дата совершения платежа                      |
| paid_lesson    | Урок, за который произведена оплата (опционально) |
| paid_course    | Курс, за который произведена оплата (опционально) |
| payment_amount | Сумма оплаты                                 |
| type_pay       | Способ оплаты: наличные или безналичный расчёт |

Также реализована оплата через Stripe.

### Приложение study

Содержит две основные модели: курс и урок.

#### Модель Course (Курс)

| Поле        | Описание                     |
|-------------|------------------------------|
| name        | Название курса               |
| preview     | Изображение-превью курса     |
| description | Подробное описание курса     |

#### Модель Lesson (Урок)

| Поле        | Описание                                     |
|-------------|----------------------------------------------|
| name        | Название урока                               |
| preview     | Изображение-превью урока                     |
| description | Описание урока                               |
| url         | Ссылка на видеоурок                          |
| course      | Связь с курсом (внешний ключ, один ко многим) |

Между курсом и уроками установлена связь "один ко многим": один курс может содержать несколько уроков, каждый урок принадлежит только одному курсу.

## 8. Периодические задачи

Проект настроен для работы с Celery и celery-beat для выполнения периодических задач.
Настройки Redis вынесены в переменные окружения.

Добавлена асинхроная рассылка писем пользователям об обновлении материалов курса.
Пользователь может обновлять каждый урок курса отдельно. Добавлена проверка на то, что уведомление 
отправляется только в том случае, если курс не обновлялся более четырех часов.

С помощью celery-beat реализована фоновую задачу, которая будет проверять пользователей по дате 
последнего входа по полю last_login и, если пользователь не заходил более месяца, блокировать его
с помощью флага is_active. Задача сделана периодической (запуск каждый день в 3:00, расписание в настройках celery-beat).

# Запуск проекта с использованием Docker Compose

Этот файл `docker-compose.yml` определяет конфигурацию для запуска всех необходимых сервисов вашего проекта: 
веб-приложения Django, базы данных PostgreSQL, Redis и Celery (worker и beat).

## Предварительные требования

*   [Docker](https://docs.docker.com/get-docker/) установлен и работает.
*   [Docker Compose](https://docs.docker.com/compose/install/) установлен (обычно входит в состав Docker Desktop).
*   Файл `.env` с необходимыми переменными окружения (например, `DATABASE_NAME`, `DATABASE_USER`, `DATABASE_PASSWORD`).

## Процесс запуска

### 1. Сборка и запуск всех сервисов

Перейдите в корневую директорию вашего проекта (где находится файл `docker-compose.yml` и `Dockerfile`). 
Затем выполните следующую команду:

```bash
docker-compose up --build
```

или 

```bash
docker-compose -f docker-compose.yml up
```

## 9. Настройка удаленного сервера и деплоя

▌1. Предварительные Требования

Перед началом развертывания убедитесь, что у вас есть:

•  Удаленный сервер (VM): Настроенный и доступный по SSH. Рекомендуется использование облачных провайдеров, таких как Яндекс.Облако.
•  Docker: Установленный на удаленном сервере.
•  Git: Установленный на удаленном сервере.
•  GitHub Аккаунт: С настроенным репозиторием для вашего проекта.
•  Docker Hub Аккаунт: Для хранения Docker-образов.
•  SSH Ключ: Пара публичного/приватного ключей для безопасного доступа к серверу.

▌2. Настройка Удаленного Сервера

▌2.1. Обновление Системы и Установка Docker

1. Подключитесь к вашему серверу по SSH:
`ssh ваш_пользователь@IP_АДРЕС_СЕРВЕРА`
2. Обновите список пакетов и установленные пакеты:
`sudo apt update && sudo apt upgrade -y`
 
2.2. Настройка SSH для CI/CD
1. Скопируйте ваш публичный SSH ключ на сервер:
  Убедитесь, что ваш публичный ключ (например, ~/.ssh/id_rsa.pub) добавлен в файл ~/.ssh/authorized_keys на удаленном сервере.

3. Настройка GitHub Secrets
Для безопасной передачи чувствительных данных в CI/CD пайплайн, настройте следующие секреты в вашем GitHub репозитории (Settings -> Secrets and variables -> Actions):

•  SSH_KEY: Ваш приватный SSH ключ (без пароля, если он есть).
•  SSH_USER: Имя пользователя для SSH доступа к серверу.
•  SERVER_IP: Публичный IP-адрес вашего удаленного сервера.
•  DOCKER_HUB_USERNAME: Ваш логин в Docker Hub.
•  DOCKER_HUB_ACCESS_TOKEN: Ваш токен доступа к Docker Hub.
•  SECRET_KEY: Секретный ключ Django вашего приложения.
•  DATABASE_NAME: Имя вашей PostgreSQL базы данных.
•  DATABASE_USER: Пользователь PostgreSQL.
•  DATABASE_PASSWORD: Пароль пользователя PostgreSQL.
•  DATABASE_HOST: Хост для подключения к базе данных (обычно db если база в Docker Compose, или IP-адрес сервера).
•  DATABASE_PORT: Порт PostgreSQL (обычно 5432).

4.  GitHub Actions Workflow
Рабочий процесс CI/CD определен в файле .github/workflows/ci.yml.

4.1. Описание Workflow

Workflow состоит из трех основных этапов (jobs):

1. test:
  •  Запускает PostgreSQL в Docker-контейнере для тестов.
  •  Устанавливает зависимости Python.
  •  Выполняет миграции базы данных.
  •  Запускает Django тесты.
  •  Важно: Для этого шага используются переменные окружения, которые могут отличаться от продакшена (например, DATABASE_HOST может быть localhost или db в зависимости от того, как настроен сервис Postgres в GitHub Actions).

2. build:
  •  Подключается к Docker Hub.
  •  Собирает Docker-образ вашего приложения с использованием тега, соответствующего хешу коммита (${{ github.sha }}).
  •  Пушит собранный образ в Docker Hub.

3. deploy:
  •  Использует webfactory/ssh-agent для безопасного подключения к вашему удаленному серверу.
  •  Подтягивает последний Docker-образ из Docker Hub.
  •  Останавливает и удаляет предыдущий контейнер с именем myapp.
  •  Запускает новый контейнер myapp, пробрасывая порт 80 хоста на порт 8000 контейнера (-p 80:8000).
  •  Важно: Все необходимые переменные окружения (SECRET_KEY, DATABASE_HOST, ALLOWED_HOSTS и т.д.) должны быть переданы в docker run команду через -e флаг. 
В текущем примере они передаются через SSH, но в реальной ситуации их лучше передавать напрямую в docker run команду.

▌4.2. Запуск Workflow

•  Автоматический запуск: Workflow автоматически запускается при каждом push или pull_request в репозиторий.
•  Деплой: Для деплоя на продакшн, вам нужно будет вручную инициировать workflow (например, создав тег или изменив ветку), либо настроить его на автоматический деплой при слиянии в определенную ветку (например, main или production).
•  Локальная проверка: Перед пушем на GitHub, рекомендуется локально протестировать Docker-образ с помощью docker-compose.

▌5. Деплой на Сервер

После того, как GitHub Actions успешно прошел этапы test и build, этап deploy попытается развернуть приложение на вашем сервере.

1. Подключитесь к серверу по SSH.
2. Проверьте статус контейнера:
`docker ps`
Вы должны увидеть контейнер myapp, работающий, и порт 80 проброшенный на 8000.
3. Проверьте логи контейнера:
`docker logs myapp`
Ищите ошибки, связанные с подключением к базе данных, Celery, или Django.
4. Проверьте доступность приложения:
  Откройте в браузере http://IP_АДРЕС_СЕРВЕРА.
  •  Если вы получаете 404 на корневом URL, это означает, что маршрут / не настроен в urls.py. Исправьте urls.py и перезапустите контейнер (или пересоберите образ и запустите новый workflow деплоя).
  •  Если приложение не отвечает, проверьте:
    *  Правильность передачи переменных окружения в docker run (особенно ALLOWED_HOSTS и SECRET_KEY).
    *  Настройки базы данных (DATABASE_HOST, DATABASE_NAME, DATABASE_USER, DATABASE_PASSWORD). Убедитесь, что PostgreSQL на сервере настроен на прием внешних подключений.
    *  Настройки фаервола на сервере (порт 80 должен быть открыт).
